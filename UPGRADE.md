# Upgrade

**English** | [简体中文](UPGRADE.zh-CN.md)

This is the upgrade part of the [agent-mesh guide](README.md). The labels `[LOCAL]`, `[BOT-CLOUD]` and `[GROK-UI]` are explained under [Execution location labels](README.md#execution-location-labels).

The local repository, the clone on the Bot cloud computer and the saved routine prompt are separate: changing files on the Mac does not update the other two. A reply convention already appended to a project's `AGENTS.md` is not updated either: copy the filled-in template from `~/.local/lib/agent-mesh/templates/` again, or, for a copy from v0.8.0 or later, run `python3 scripts/reply_convention.py refresh <repository>/AGENTS.md`. `./update.sh` refreshes the copies in `~/.local/lib/agent-mesh/templates/` itself. The [changelog](CHANGELOG.md) says which parts each version changes.

## Which version you come from

Find the row for the version you have; `./install.sh --version` prints it. Every row ends with `./check.sh`.

| You have | Run | Besides the update of this Mac |
|---|---|---|
| v0.10.0 and later | `agent-mesh update` (or `./update.sh`) | One cloud update request when the cloud side changed, which Grok Bot runs without asking. Nothing to paste unless the routine stub itself changes. |
| v0.8.2 – v0.9.1 | `./update.sh` | One cloud update request, which Grok Bot runs without asking; then the [routine stub](#routine-stub) is pasted once for each Bot, and this Mac asks each Bot to confirm it. |
| v0.4.0 – v0.8.1 | `git pull --ff-only && ./update.sh` | The routine stub is pasted first; Grok Bot then runs the update request from this Mac by itself, with no confirmation in a Grok conversation ([First cloud update with this version](#upgrade-with-updatesh)). From v0.6.0 or earlier the engine is upgraded on both computers ([Reason Network engine](#reason-network-engine)). Pull first: the `update.sh` of v0.4.0 – v0.6.0 stops before pulling when the engine has already updated itself. |
| v0.3.0 and earlier | `git pull --ff-only && ./update.sh` | Checkouts up to v0.3.0 have no `update.sh` and this Mac has no record of the cloud side, so `./update.sh` does the cloud step by hand, as with `--manual`: the cloud command block is run in a Grok conversation, then the routine stub is pasted. |

On a Mac first installed with v0.8.0 or earlier, `./update.sh` may also correct the engine settings and restart the engine and the relay once ([Engine settings](#reason-network-engine)).

## Upgrade with update.sh

In the repository on `[LOCAL]`, run:

```bash
./update.sh --lang <en|zh-CN>
```

It first fetches the upstream branch with its tags and moves the checkout forward to the newest release tag `vX.Y.Z` on that branch (skip it with `--no-pull`), then compares each part with what this Mac deployed. Commits on the branch after the newest release are not taken. When the checkout already contains that release, or the branch has no release tag, it uses the checkout as it is; when the checkout has commits that are not in the release, it stops before changing anything and prints the command to use the checkout as it is. When tracked files of the checkout have uncommitted changes, it lists them (up to 20, then the total) instead of pulling: in a terminal without `--yes` it asks once whether to continue with the checkout as it is, which is the same as `--no-pull`; otherwise it stops and prints the full command to do so. If the changes touch the cloud scripts, the release check below still stops the update before the cloud is touched.

| Part | Compared | When it differs |
|---|---|---|
| Relay | the installed `agent_relay.py` and its login service file against this checkout, with the Python the relay is fixed to | installed and restarted; if the new relay does not come up, the previous one is put back |
| Engine | `~/.local/bin/reason-network` against the version this release pins, whether the running daemon started after the binary was last replaced, and whether `auto_update` and `lan` are off where the engine reads them | an older engine is upgraded ([Reason Network engine](#reason-network-engine)); a daemon still running a replaced binary is restarted; settings that are not off are corrected and the daemon is restarted; a newer or unrecognised engine stops the update |
| dsh plugin | the installed plugin file, if the bridge is installed | the file is replaced; `~/.dsh/cordis.patch.yml` and your bridge settings stay as they are; quit and reopen dsh |
| Cloud scripts | `box/rn-cloud.sh`, `box/rn-fetch.py`, `box/rn-cloud-update.sh`, `box/rn-cloud-add-bot.sh`, `box/rn-routine.py` and the rules templates `prompts/routine-body.md` and `prompts/routine-body.zh-CN.md` against what you last confirmed | the cloud update, below |
| Cloud setup | `box/rn-cloud-setup.sh` against what you last confirmed | the cloud update, below; it runs `box/rn-cloud-setup.sh --upgrade-engine`, which holds any cloud migration |
| Cloud engine | the Reason Network version on `[BOT-CLOUD]` this Mac last confirmed, against the pinned version | the cloud update, below; it always checks the cloud engine |
| Routine prompt | the routine stub for the chosen language (with `--full-prompt`, the complete prompt) against what you last confirmed | printed for you to paste into the routine in `[GROK-UI]`; the stub is then confirmed by a read-back ([Routine stub](#routine-stub)) |

What the Mac last confirmed is kept in `~/.local/lib/agent-mesh/deployed.json`. The plan lists the parts that differ and asks once, `Continue? [Y/n]`; `--yes` skips that question. Outside a terminal the update runs only when no answer is needed: only the relay or the dsh plugin changed, or `--yes` is given. Outside a terminal or with `--yes`, a changed routine prompt is left as it is: the cloud is updated with the request the current prompt already knows, Grok Bot keeps that prompt, and the next `./update.sh` in a terminal without `--yes` shows the new one. It still stops when the prompt must be pasted first (a cloud last confirmed with v0.8.1 or earlier, see below) or when an earlier prompt was printed but never confirmed.

The order is: this Mac first (an unfinished engine upgrade is rolled back, the engine is upgraded, the relay and the dsh plugin are replaced), then the cloud and the routine prompt. A cloud last confirmed with v0.8.2 or later is updated first, with the request its current prompt already knows; then the stub is shown, so the rules it loads are already there when you paste it. A cloud last confirmed with v0.8.1 or earlier cannot run the request with its old prompt, so the stub is shown first and the cloud update follows ([First cloud update with this version](#upgrade-with-updatesh)). Paste the prompt into the routine and answer that it is saved; a stub is then confirmed by a read-back.

**Relay Python.** The relay's login service names the Python it runs on. Since v0.9.1 that Python is fixed: it is kept in `~/.local/lib/agent-mesh/deployed.json` (`relay_python`), and `./update.sh` and `./install.sh` write the service file with it, whichever `python3` runs the script. Running `./update.sh` from another terminal or inside a virtual environment therefore no longer changes the service file or restarts the relay. An existing installation keeps the Python its service file already names, exactly as written there, even one inside a virtual environment or a temporary directory; the plan and `./check.sh` then show a reminder. A new installation takes `/opt/homebrew/bin/python3`, then `/usr/local/bin/python3`, then `/usr/bin/python3` (only with the Xcode command line tools), and never one inside a virtual environment or a temporary directory; with none of them it stops and asks for `--python`. `./install.sh --python <path>` checks the given Python (3.9+ with `ssl` and `sqlite3`), rewrites the service file of every Bot, restarts the relays and records the path once they are up; if a relay does not come up, the previous service files and the previous record stay. The relay is moved to another Python and restarted without `--python` only when the fixed one is missing or no longer works, or when the Bots' service files name different ones (the first Bot's is used); the plan says so.

**Cloud update.** `./update.sh` sends Grok Bot an ordinary message from this Mac, through the relay: `agent-mesh update <tag> <commit> <request>`. The rules the routine stub loads (in v0.8.2 – v0.9.1, the routine prompt) have a rule for exactly this message: when its sender is the same person as the cloud (the user's own Mac) and the body is exactly that one line, Grok Bot runs `bash /workspace/agent-mesh/box/rn-cloud-update.sh '<tag>' '<commit>' '<request>'` without asking and replies with the whole output. The same message from anyone else is not run. `./update.sh` waits up to 15 minutes, finds the reply in this Mac's Reason Network database by its request number, compares it and records the cloud as updated. The routine keeps running and the relay is not stopped for the cloud update.

`box/rn-cloud-update.sh` on `[BOT-CLOUD]` checks the tag, the commit and the request number, refuses a tag older than the clone's version (it never downgrades), stops if the clone has local changes (listing them), fetches the tag, checks that it points to the release commit, checks it out (a detached HEAD) and then runs the same script from the new checkout, which runs `box/rn-cloud-setup.sh --upgrade-engine` and prints the closing lines. Its first line is `agent-mesh-result request <request>`; on any failure it prints a `STOP:` line instead of the closing lines. A failed engine step keeps the new checkout.

The cloud is recorded as updated only when the reply has the closing lines the script prints itself, each starting with `agent-mesh-result`: the release commit, the checksum of each of the eight cloud files and `DONE <tag>`, and the `engine:` lines with the pinned version, the pinned build and `launcher ok`. A `STOP:` line, another commit or a different checksum leaves it unrecorded; `./update.sh` shows the reason, and the next run sends a new request. When no reply comes within 15 minutes, Grok Bot may still be working (its result also shows in Grok): the next `./update.sh` first looks for the reply to the saved request and records it, and sends a new request only if there is none. A reply to a request for another version, or sent before this checkout changed, is never recorded.

**First cloud update with this version.** A cloud last confirmed with v0.8.1 or earlier has no `box/rn-cloud-update.sh`, and its routine prompt has no rule for the update request. The routine stub is pasted first; then `./update.sh` sends the one-line request, followed by a line `lang=<en|zh-CN>`. On that old cloud the stub cannot load its rules yet, so its step 3 runs one fixed command with the ids of the run's messages: it fetches them, and for a message that starts with `agent-mesh update <tag>` it fetches that release tag and runs the tag's `box/rn-cloud-update.sh`. That script checks the sender (the user's own Mac), the request and the tag itself before it changes anything, updates the clone as above, sends the reply and tells Grok Bot to load the new rules in the same run. No confirmation in a Grok conversation is needed. After the reload, the run handles its other messages with the new rules.

If no reply comes in time or the cloud update fails, the old cloud cannot load the stub's rules, so `./update.sh` prints the complete prompt for you to paste back; the routine then works as before, and the next `./update.sh` first looks for the reply to the saved request and otherwise tries again. A Mac without any record of the cloud side (v0.3.0 or earlier) does the cloud step by hand, as with `--manual`, and shows the stub after that.

The cloud installs only published releases. Before anything changes, `./update.sh` checks online that the release tag `v<VERSION>` exists in the repository the cloud installs from (the public repository, or the one given with `--repo-url`) and that `box/rn-cloud.sh`, `box/rn-fetch.py`, `box/rn-cloud-setup.sh`, `box/rn-engine.py`, `box/rn-cloud-add-bot.sh`, `box/rn-routine.py`, `prompts/routine-body.md`, `prompts/routine-body.zh-CN.md` and `box/rn-cloud-update.sh` in this checkout match it; the rest of the checkout may differ, and it need not be committed or at its upstream. If the tag cannot be fetched or a file differs, the update stops before stopping the relay or touching the engine, and nothing is changed. `--plan` shows the result of this check. The check needs network access only when the cloud is part of the update.

- `./update.sh --plan` only shows the comparison and the steps; it changes nothing in the deployment. Without `--no-pull` it may still fast-forward the checkout first.
- Exit code 3 means answers in a terminal are needed; nothing was changed. Exit code 1 means not everything was done, for example no reply from Grok Bot yet; the summary says which part. When every part was done and only the final `./check.sh` failed, the summary says so separately.
- **The `agent-mesh` command.** `./update.sh` (except with `--plan`) and `./install.sh` record this checkout in `~/.local/lib/agent-mesh/deployed.json` and write `~/.local/bin/agent-mesh`. `agent-mesh update [options]` and `agent-mesh check [options]` then run `./update.sh` and `./check.sh` of the recorded checkout from any folder. Running `./update.sh` in another checkout moves the command there. If `~/.local/bin` is not in `PATH`, the script says so. A file at that path that agent-mesh did not write is left alone. `./uninstall.sh --level program` removes the command.
- `./update.sh --manual` updates the cloud by hand instead: it stops the relay, asks you to pause the routine in `[GROK-UI]`, prints a message with the command block above for Grok Bot (send it directly in chat, not through the routine) together with the commit and checksums its reply must show, asks you to paste Grok Bot's whole reply followed by a line with only a dot (`.`) and compares it, prints the new routine prompt to paste, asks you to resume the routine, and finally starts the relay. If you answer no, press Ctrl-C or a step fails, the relay that was running before is started again, and you are reminded if the routine is still paused. Run `./update.sh` again to continue from that step; finished steps are not repeated unless the version moved on in between.
- Grok Bot must not reset, clean or stash anything; a clone with local changes stops the update. Sort out the files it lists with Grok Bot, then run `./update.sh` again.
- Updating an installation from before Bot address names: it keeps the name `bot`. An installation with another Bot address name cannot go back to a version without Bot address names.
- Updating to v0.8.0: the address of an existing installation stays, also `bot`. Record the Bot's name in Grok with `./install.sh --grok-name '<its name in Grok>'`; it changes only the label shown next to the address.
- Updating from v0.8.0 or earlier: the cloud update also moves the cloud engine to `box/bin/engine` and checks it ([Reason Network engine](#reason-network-engine)).
- First update from v0.3.0 or earlier: run `git pull` yourself once, because older checkouts have no `update.sh`. Without a record, the cloud parts and the prompt count as unknown, so the cloud update (by hand, as with `--manual`) and the prompt step run once.
- The script cannot see the routine or the cloud computer: it relies on your answers and on what Grok Bot's reply reports.

## Routine stub

Since v0.10.0 the routine prompt is a fixed short text, the routine stub. On every run Grok Bot first runs `bash /workspace/agent-mesh/box/rn-cloud.sh instructions 1`, whose output is the rest of the prompt: the rules, rendered on `[BOT-CLOUD]` from the templates `prompts/routine-body.md` and `prompts/routine-body.zh-CN.md` of the cloud's checkout. A cloud update that changes the rules therefore needs no paste. You paste again only when the stub itself changes (its first line names its version). The stub is the same English text for both languages, so changing the language needs no paste either: the read-back request below carries it to `[BOT-CLOUD]`. An added Bot's stub also names that Bot.

After you paste the stub and answer that it is saved, `./update.sh` sends the Bot a read-back request: `agent-mesh stub <request>` and a line `lang=<en|zh-CN>`. The loaded rules pass it to `rn-cloud.sh request`, whose reply names the stub version that run loaded and the language the cloud renders its rules in from then on. The prompt is recorded as confirmed only when they match what you pasted; otherwise `./update.sh` shows what differs and the next run sends a new read-back. A reply showing that the run did not load its rules through the stub means the stub is not in the routine yet: the next `./update.sh` shows the stub again to paste. When no reply comes in time, the prompt stays unconfirmed: the next `./update.sh` first looks for a late reply to the saved request and records it, and if there is none it shows the stub again to paste and sends a new read-back. A read-back needs the Bot's relay running and the cloud update recorded first.

`./update.sh --full-prompt` shows the complete prompt instead: the stub's rules rendered on this Mac, which you paste and confirm as before, with no read-back. With it, every change of the rules needs a new paste. The option applies to that run; a later run without it shows the stub again.

## Several Bots

With several Grok Bots on this Mac ([Several Grok Bots](README.md#several-grok-bots)), one `./update.sh` covers all of them; a Mac with one Bot sees the same output as before.

- **Plan.** The result lines are for all Bots together, followed by one line per Bot in order with its relay and prompt state. A Bot that is still waiting for its cloud registration is named with `./install.sh --relay-name <name> --wake-bot`, which wakes it.
- **Pending additions.** Before the plan, `./update.sh` looks for the reply of every added Bot whose cloud registration is still pending (for example after `./install.sh --add-bot` stopped waiting) and records the ones that arrived.
- **Routine prompts.** Each Bot has its own routine prompt. Every changed prompt is shown in turn with the Bot it belongs to; paste it into that Bot's routine and confirm. Each Bot's stub is then confirmed by its own read-back. A Bot whose cloud registration is not confirmed yet is skipped. If you stop part-way, the prompts confirmed so far stay recorded and the next run asks only for the others. Changing the language needs no paste; each Bot's read-back carries it.
- **Engine and relays.** One engine step covers the relays of every Bot that is installed: they are stopped together, the engine is switched or restarted once, and they are started again together ([Reason Network engine](#reason-network-engine)). On failure every relay returns to the state it had before.
- **Cloud.** The Bots share one cloud computer, so the cloud update runs once. The request goes through the first Bot in order whose cloud registration is confirmed and whose relay runs and is registered; with none, `./update.sh` stops before sending anything and suggests `./install.sh --restart-relay`. The routines are not paused: the cloud scripts take a maintenance lock while the update runs, and the other Bots' cloud commands wait for it, up to 10 minutes.
- **`--manual`**, and an unfinished `--manual` run that `./update.sh` continues, stop every Bot's relay and ask you to pause and later resume every Bot's routine. If the run stops in between, it names the Bots whose routines are still paused.
- A Bot that is being uninstalled stops `./update.sh` until `./uninstall.sh --level bot --relay-name <name>` has finished ([Remove one Bot](UNINSTALL.md#remove-one-bot)).

## Reason Network engine

agent-mesh 0.7.0 moves the pinned engine from Reason Network 0.10.7 to 0.12.17 (0.10.7 is affected by the upstream security advisory GHSA-84r9-56w3-xqp9). `./update.sh` upgrades the engine on both computers. It works from any earlier agent-mesh version in one run, so you do not need to install 0.6.0 first.

On `[LOCAL]` the engine switch is part of the single "Continue?" question that `./update.sh` asks after showing the plan; `--yes` answers it, so the switch can also run without a terminal. The order:

1. It lists other processes that use the engine, such as open Claude Code or Codex sessions. They do not block the upgrade and keep working with the restarted daemon; restart those sessions after the update so they run the new version.
2. It downloads 0.12.17 and checks it against the SHA-256 written in `install.sh` (the same table is in `box/rn-cloud-setup.sh`), so a changed download is refused. If the download or the check fails, nothing is changed; the relay keeps running as it was.
3. It writes the upgrade record `~/.local/lib/agent-mesh/engine-upgrade.json` and stops the relay (with several Bots, the relay of every installed Bot).
4. It copies the binary and `~/.reason/network` to `~/.local/lib/agent-mesh/engine-backup-<UTC time>/` (mode 700), replaces the binary, restarts the daemon, and checks that the running daemon started after the replacement, reports 0.12.17, still lists the team's machines and answers `who`.
5. It installs this checkout's relay, starts it (every Bot's relay) and checks that it registered under its name on the new daemon. The previous relay stays in `~/.local/lib/agent-mesh/rollback/` until step 6.
6. It marks the upgrade as finished and removes the upgrade record and the previous relay.

Restarting a daemon that still runs a replaced binary takes the same steps, with a daemon restart instead of step 4. Since v0.9.0 the new relay is installed only after the engine step; earlier versions installed it on the old engine first.

If step 4 or 5 fails, or you press Ctrl-C, the old binary is put back and the daemon is restarted on it, the previous relay program and login service files come back, and each relay returns to the state it had before (one that was stopped stays stopped). The state directory is not restored: the newer engine only adds tables and columns, 0.10.7 opens the upgraded database, and mail that arrived after the switch stays. A daemon that does not exit after `reason-network stop` is ended with SIGTERM, then SIGKILL. Going back to 0.10.7 does not bring back what 0.12 already dropped or what 0.10.7 does not know: ordinary sessions forgotten while 0.12 ran, with their unread mail (the relay's and the cloud's mailboxes are not forgotten); and newer team signing attestations and `[folders]` settings, which 0.10.7 drops the next time it saves the team state. CLI sessions created under 0.10.7 after a rollback are not mailboxes until 0.12's `listen` marks them again after the next upgrade. If the old engine cannot be confirmed running, the script prints the manual steps and keeps the record `~/.local/lib/agent-mesh/engine-upgrade.json`; `./check.sh` reports FAIL, and the next `./update.sh` rolls the switch back before anything else. Restoring the state directory from the backup is only the last manual step and loses the mail received after the switch.

The backup holds a copy of this computer's engine identity and received messages. Delete it once `./check.sh` passes; `./uninstall.sh --level identity` also removes it, with the deployment record.

`./update.sh` never downgrades: a newer or unrecognised engine stops it, and `./install.sh` stops on an older engine and points to `./update.sh`. If the binary is already 0.12.17 but the running daemon started before the binary was replaced, `./update.sh` offers to restart the daemon.

On `[BOT-CLOUD]`, every cloud update runs `bash /workspace/agent-mesh/box/rn-cloud-setup.sh --upgrade-engine` from the new checkout, which checks the cloud engine and upgrades it the same way: pinned checksum, backup in `box/engine-backup-<UTC time>/`, switch, check of the running daemon, and on failure the old binary back if it was a pinned build. An engine that is already 0.12.17 is only checked; its daemon is started or restarted when needed.

The cloud engine lives at `box/bin/engine/reason-network`; `box/bin/reason-network` is a launcher for commands run by hand, which refuses to run without `REASON_NETWORK_HOME` and always disables automatic updates. The step moves an engine still at `box/bin/reason-network` (from v0.8.0 or earlier) to `box/bin/engine` and writes the launcher. It decides whether the current engine can be trusted from its bytes alone, without running it: a binary that is not one of the builds pinned in `box/rn-engine.py` (for example one replaced by an automatic update, or the earlier pinned 0.10.7, which has no pinned build) is replaced with the pinned version without being run; it is kept in the backup and never put back. If the step fails after the pinned build is in place, it prints manual steps that use only the new binary; if the pinned build could not be put in place, nothing that starts the engine is changed, and the step says to fix the cause and run it again. Grok Bot's reply must show the line `engine: reason-network 0.12.17 running (daemon pid …)`, `engine: pinned build <sha256> at box/bin/engine/reason-network` with a pinned build, and `engine: launcher ok`; `./update.sh` compares them and records the cloud engine only when they match. A line `engine: note: other engine daemons run from box/bin` lists daemons started earlier from the old path; they cannot replace the engine any more, and the step does not stop them ([Troubleshooting](README.md#troubleshooting)). A cloud engine that is a pinned build newer than 0.12.17 is left as it is, and the step fails.

While one side runs 0.10.7 and the other 0.12.17, in either order, messages, receipts and re-forwards keep working: agent-mesh 0.6.0 and later read both engines' output. Upgrade the Mac and the cloud in the same run when you can. After the upgrade, Reason Network 0.12's rules apply: its default relays are under `compute.reasonmachines.com` ([Network](README.md#network)), and ordinary sessions offline for more than a day are forgotten together with their unread messages ([Network and usage](README.md#network-and-usage)).

**Engine settings.** agent-mesh turns off the engine's `auto_update` and `lan` in `~/.reason/network/config.toml`. The engine reads these two keys only above the first `[table]` line of that file. On a Mac first installed with v0.8.0 or earlier the two lines can sit inside a table, where they turn nothing off, so automatic updates and LAN discovery stayed on while `./check.sh` reported them off. Since v0.9.1, `./check.sh` and `./update.sh` check the whole file: the two keys must be off above the first table, and no table may name them. When that is not so, the plan shows `security hardening: correct the engine settings and restart the engine` and asks its one question (`--yes` answers it). The step runs like a daemon restart: it writes the upgrade record, removes the lines `auto_update = false` and `lan = false` that an earlier version appended inside a table, puts the two lines at the top of the file, restarts the daemon, starts every relay again and checks their registration. If the engine is also upgraded in this run, the settings are corrected before the switch.

A corrected file is not enough while the old daemon still runs with what it loaded at its start. Before writing the file, `./update.sh` therefore notes the repair in `~/.local/lib/agent-mesh/deployed.json` (`engine_config`), and removes the note only when the running daemon started after the file was written, or when no daemon runs. When it removes lines from a table, it first keeps the file as it was next to it, as `config.toml.agent-mesh.bak`, and deletes that copy together with the note. If the run is interrupted between the write and the restart, the note stays: `./check.sh` reports FAIL, the next `./update.sh` shows the same plan line and restarts the daemon. A rolled-back step does not undo the corrected file. Restarting the relay rings the doorbell again for messages the cloud has not confirmed yet, so when the relays still hold such messages the plan says how many, and the step waits for them (up to 15 minutes, then it stops without restarting; run `./update.sh` again later). The check covers the file as the engine writes it. If the lines above the first table use quoted keys or multi-line strings, or the file names `auto_update` or `lan` anywhere else in another form than those two appended lines (another true/false spelling, spacing or quoting, a value that is neither true/false nor a quoted string, a dotted key, or a table of that name), it does not guess: `./update.sh` stops before changing anything and `./check.sh` reports FAIL, `./check.sh` points to `./update.sh`, which says what to change by hand. `./update.sh` also notes the repair, so the run after your edit restarts the daemon and it loads the corrected file. A person or a folder that happens to be named `auto_update` or `lan` (a line such as `lan = "hold"` inside a table, with a quoted string value) is left alone and does not stop anything.

Check the result with `./check.sh`. It reports the engine version against the pinned one, whether the running daemon runs the installed binary, an unfinished engine upgrade, whether the relay registered on the running daemon, and the cloud engine version this Mac last confirmed. For up to 11 minutes after a daemon or relay restart, the registration line is SKIP while the relay registers again.

Known limitations:

- The daemon's start time and the binary's change time are compared in whole seconds, so a daemon the old binary started in the same second as the replacement counts as fresh. On Linux a daemon still running a replaced binary is also caught because its program shows as deleted; macOS has no such check.
- The relay records its registration after `listen` returns. If the daemon restarts in between, `./check.sh` can report a stale registration until the next `listen`, a few seconds later.
- Relay startup work before the first registration (catching up on missed mail, re-sends, the webhook) can use up the 45-second registration wait; the restart then counts as failed and is rolled back. `AGENT_MESH_REGISTER_WAIT=<seconds>` raises the wait.
- If a rollback succeeds but the relay does not start again, the upgrade record is already removed, so the next `./update.sh` does not retry; run `./install.sh --restart-relay` as the message says.
- `./check.sh` does not compare the cloud scripts' checksums; it reports only the cloud engine version this Mac last confirmed. `./update.sh` compares the checksums when it guides the cloud step, and every `rn-cloud.sh` command checks the engine's bytes on `[BOT-CLOUD]`.

## Manual upgrade

When the relay, the cloud scripts and the routine prompt all change, update them together in this order, so that no doorbell rings while some parts are old. With several Bots, do steps 1, 2 and 4 for every Bot (an added Bot's service is `com.local.agent-relay.<name>`, and each Bot has its own routine prompt); `./install.sh --restart-relay` in step 5 restarts every Bot's relay:

1. On `[LOCAL]`, stop the relay: `launchctl bootout "gui/$(id -u)/com.local.agent-relay"`. Messages that reach the Mac from now on stay unread in the local engine and ring no doorbell.
2. In `[GROK-UI]`, pause the routine and wait until no run is active.
3. Have Grok Bot update `/workspace/agent-mesh` on `[BOT-CLOUD]` to the release tag (ask it directly in chat, not through the routine). Use the command block `./update.sh` prints, which checks the tag commit and the cloud scripts' checksums before checking the tag out; a plain `git pull` runs files nobody checked.
4. In `[GROK-UI]`, replace the saved routine prompt and resume the routine. The relay is still stopped, so no doorbell rings yet.
5. On `[LOCAL]`, update the repository and run `./install.sh --restart-relay`, or rerun the full install: `./install.sh --name <team-name> --lang <en|zh-CN>`. Neither upgrades an older Reason Network: `--restart-relay` keeps the engine you have, and the full install stops on an older engine. Upgrade the engines with `./update.sh` ([Reason Network engine](#reason-network-engine)), or by hand on the cloud with `bash /workspace/agent-mesh/box/rn-cloud-setup.sh --upgrade-engine` while the routine is paused. An already configured webhook is not asked for again; the installer copies the new `agent_relay.py` and starts the relay service, which first catches up from `network.db` and then picks up the messages that arrived while it was stopped. If the new relay does not come up, the installer puts the previous one back. The full install also shows the agent wiring plan again and asks for confirmation.

While the relay is stopped the Mac gets no pushes, and messages wait in the local engine. Keep the stop short: a reply the cloud signed more than 15 minutes before the relay forwards it is refused as stale and is not delivered. If step 3 or 4 fails, start the old relay again with `launchctl bootstrap "gui/$(id -u)" ~/Library/LaunchAgents/com.local.agent-relay.plist` to return to the state before the upgrade.

To roll back receipts and re-rings later, go in this order so that an old relay never receives a receipt:

1. On `[LOCAL]`, set `GOT_TIMEOUT_SECONDS=0` in `~/.config/agent-relay/env`, restart the relay with `launchctl kickstart -k "gui/$(id -u)/com.local.agent-relay"`, keep the routine running and wait until `~/Library/Logs/agent-relay.log` shows `pending: 0` and `alerts: 0` (while the webhook delivers, at most about `GOT_DONE_SECONDS × (GOT_MAX_RERINGS + 1)`).
2. In `[GROK-UI]`, pause the routine and wait until no run is active.
3. Have Grok Bot roll `/workspace/agent-mesh` back on `[BOT-CLOUD]` and check that the cloud engine's outbox is empty, then wait a few minutes so the relay still handles any receipt on its way.
4. Restore the previous routine prompt and resume the routine.
5. Roll back the relay on `[LOCAL]` last.
